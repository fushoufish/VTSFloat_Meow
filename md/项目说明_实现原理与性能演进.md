# VTSFloat_Meow 项目说明

> 本文按“实现原理”来解释项目的工作方式，并记录从最初版本到当前版本遇到的性能瓶颈。

## 1. 项目是做什么的

VTSFloat_Meow 把 VTube Studio（VTS）中的透明 Live2D 模型显示到游戏或其他窗口上方。它本身不修改游戏进程，也不向游戏注入 DLL；VTS 负责渲染模型，本项目负责接收画面、保留透明区域并显示为桌面置顶层。

可以把它理解成三部分：

```text
VTube Studio                 VTSFloat_Meow                         游戏
模型渲染 ──Spout共享纹理──> D3D11接收/缩放 ──透明分层窗口──> 作为桌面叠加层
```

VTS 仍然是模型的“画师”，VTSFloat_Meow 是“透明画框”。Spout 不是一个需要每次单独启动的播放器，而是已经编译进项目的共享纹理通信库。

## 2. 当前技术栈

| 模块 | 当前实现 | 作用 |
| --- | --- | --- |
| 语言 | C++17 | 主程序和渲染循环 |
| 窗口 | Win32 分层窗口（`WS_EX_LAYERED`） | 显示透明像素、置顶、鼠标穿透 |
| 图形设备 | Direct3D 11 / DXGI | 创建 GPU 设备、读取显卡和显示器信息 |
| 画面传输 | 项目内置 Spout2 DirectX 接收端 | 从 VTS 取共享纹理，不经过网络和磁盘 |
| 缩放 | D3D11 GPU shader（性能/平衡/质量三档） | 在显卡上完成模型缩放和滤波 |
| 最终上屏 | 32 位 BGRA DIB + `UpdateLayeredWindow` | 把透明画面交给 Windows 桌面合成器 |
| 性能统计 | Windows PDH GPU Engine + DXGI 显存查询 | 显示本程序 GPU 占用、GPU 内存和帧耗时 |
| 设置 | `%LOCALAPPDATA%\vts_overlay_layered.ini` | 保存位置、尺寸、帧率、GPU、外观等设置 |
| 构建 | CMake + MSVC，脚本为 `native/build_native.ps1` | 生成根目录的 `VTSFloat_Meow.exe` |

入口文件是根目录的 `VTSFloat_Meow.exe`。关键源码集中在 `native/overlay_layered.cpp`，Spout2 源码位于 `native/third_party/Spout2`。

## 3. 工作原理（简明版）

### 3.1 什么是透明画面

VTS 输出的不只是红、绿、蓝三个颜色，还包括一个透明度通道 Alpha（通常记为 `A`）：

- `A = 0`：完全透明，游戏能看见；
- `A = 255`：完全不透明，显示模型；
- 中间值：半透明。

桌面合成时可以粗略理解为：

```text
最终颜色 = 模型颜色 × Alpha + 背景颜色 × (1 - Alpha)
```

因此模型外面的透明像素不会遮住游戏，模型边缘的半透明像素可以自然抗锯齿。当前程序使用预乘 Alpha 的 BGRA 数据，并在 `UpdateLayeredWindow` 中以 `AC_SRC_ALPHA` 交给 Windows 合成。

### 3.2 Spout 在做什么

Spout 是同一台 Windows 电脑上不同图形程序之间共享 GPU 纹理的一种方式。VTS 把一张 DirectX 纹理注册成发送端，名称为 `VTubeStudioSpout`；本程序按这个名称查找发送端，并在自己的 D3D11 设备上接收。

它不是“截图后保存成 PNG 再读取”，也不是网络串流，所以正常情况下不会产生磁盘 I/O 和网络延迟。共享纹理属于发送端所在的 GPU，因此接收端最好使用同一块 GPU。

### 3.3 为什么必须关注 GPU

Spout 纹理是显卡资源。如果 VTS 在独显、叠加层却强行在核显打开，系统可能需要跨适配器复制，甚至无法打开共享句柄，表现为黑屏、画面停止或卡死。因此当前的“自动 GPU”策略会优先跟随 Spout 发送端；用户手动选择不同 GPU 时，程序会提示并可以重启 VTS 使两边统一。

## 4. 一帧画面经过的完整管线

下面是程序每一帧的大致过程：

```text
① 读取 VTS Spout 发送端
        ↓
② D3D11 接收共享纹理
        ↓
③ 检查尺寸、格式和宽高比
        ↓
④ GPU 缩放/滤波（性能、平衡或质量）
        ↓
⑤ 复制到带 Alpha 的 32 位 BGRA DIB
        ↓
⑥ UpdateLayeredWindow 提交透明窗口
        ↓
⑦ Windows 桌面合成到游戏上方
```

### 步骤 1：启动和选择设备

启动时程序会枚举 DXGI 显卡、读取上次的设置、创建 Win32 窗口和工具栏。检测到 VTS Spout 后，记录发送端 GPU，并用对应适配器创建 D3D11 设备。窗口默认置顶；点击“完成”后启用鼠标穿透。

### 步骤 2：接收共享纹理

Spout 接收端从 VTS 获得最新纹理和帧计数。没有新帧时不会重复做昂贵的缩放和拷贝。发送端分辨率变化时（例如 VTS 画布比例改变），程序会重建中间资源。

### 步骤 3：处理宽高比

程序区分“比例锁定”和“自由拉伸”：

- 锁定时：目标高度按 Spout 实际宽高比计算，避免启动时短暂拉伸；VTS 改变画布比例时自动同步。
- 自由时：窗口可以横向或纵向单独拉伸，适合用户明确需要非等比效果的情况。

### 步骤 4：GPU 缩放

目标窗口尺寸与 VTS 发送尺寸不一致时，当前默认使用 D3D11 双线性缩放。性能档使用邻近采样，质量档使用更高质量的 GPU 滤波。缩放在 GPU 中完成，避免旧版本每帧在 CPU 上逐像素计算。

### 步骤 5：生成透明 DIB

最终像素进入 32 位 BGRA DIB。DIB 只是 Windows 分层窗口接口需要的上屏缓冲，不是中间文件，也不会写入磁盘。

### 步骤 6：分层窗口上屏

程序调用 `UpdateLayeredWindow` 更新整个透明窗口。窗口使用 `BLENDFUNCTION` 的 `AC_SRC_ALPHA`，所以每个像素自己的 Alpha 会保留下来。锁定悬停淡化时，只改变一次全局 Alpha，并在约 180ms 内平滑插值，不会重新渲染模型；个性化对话框预览时则只调整模型像素，边框保持不透明。

### 步骤 7：输入、工具栏和托盘

解锁时，顶部工具栏提供 GPU、帧率、比例、个性化、调试、完成和 GitHub 按钮。快捷键按钮以“锁定/解锁 …”显示，默认组合键为 `Ctrl+Shift+L`。GitHub 按钮左侧紧邻“—”隐藏按钮，仓库 URL 目前留在源码常量中，补入地址后即可打开。锁定时窗口开启 click-through，游戏能直接收到鼠标；调试模式可保留一个小“解锁”入口。系统托盘支持隐藏/显示、主屏居中重置和退出。

普通锁定会隐藏边框；调试模式锁定时会继续绘制边框，并保留“解锁”按钮，方便确认窗口边界和模型位置。

自定义边框颜色使用“色相/饱和度圆盘 + 亮度滑块”。圆盘选择色相和饱和度，右侧亮度可以从 0% 调到 100%，所以黑色、灰色和白色都可以精确选取。

## 5. 刷新、同步和性能统计

程序有两种帧率模式：

- 固定 FPS：例如 30、45、60、120；
- 跟随窗口所在显示器：读取 Windows 的固定显示模式刷新率，窗口移动到另一块屏幕后重新计算。

这不是动态 G-SYNC/FreeSync 读取，也不会盲目追求“无限 FPS”。每次统计周期会记录请求、接收、新帧、上屏、接收耗时、缩放耗时和上屏耗时。状态栏还会通过 Windows GPU Engine 计数器显示本程序在当前 GPU 上的占用，并通过 DXGI 显示本进程的 GPU 内存使用量。

性能日志位置：

```text
%LOCALAPPDATA%\vts_overlay_layered.log
```

例如 `app_gpu_percent=25.1` 表示采样时本程序 GPU 引擎利用率约 25.1%，不是整张显卡的总占用。

## 6. 早期瓶颈与解决方向

### 6.1 Python/Qt 主线程排队

最早版本依赖 Python/Qt 事件循环接收、绘制和刷新窗口。游戏进入高负载或无上限帧率后，GUI 线程得不到及时调度，日志曾出现 GUI 队列平均数千毫秒、最大超过 10 秒。表面看是“Spout 卡”，实际是窗口消息和绘制任务在排队。

解决方式：把关键路径迁移到原生 C++，主循环使用高精度定时和 Win32 消息泵；渲染、窗口提交和 GUI 状态更新都减少不必要的阻塞。

### 6.2 DirectComposition/SwapChain 的 Present 阻塞

第二条尝试使用 DXGI SwapChain/DirectComposition。无边框游戏前台时，透明窗口的 `Present` 可能等待桌面合成器，日志出现 `present` 约 1000–5000ms，最终看起来像整个程序卡死。

解决方式：最终渲染器改为 Win32 分层窗口 + `UpdateLayeredWindow`，不再依赖 SwapChain 的 Present 节奏，也不调用会等待合成器的 `DwmFlush`。这条路径更适合当前的透明桌面叠加需求。

### 6.3 CPU 缩放和逐像素处理

当窗口放大到副屏尺寸时，CPU 逐像素缩放会明显增加每帧耗时，并和游戏争抢 CPU。早期日志中缩放耗时会随窗口面积显著增加。

解决方式：把缩放移到 D3D11 GPU shader；性能/平衡/质量三档只改变采样方式。CPU 只负责必要的资源映射和 DIB 上屏。

### 6.4 启动时比例错误、拖动后才正常

最初把默认窗口尺寸写成固定值，而 VTS 的实际 Spout 画布可能是 `1280×773`、`1280×720` 或其他比例。程序启动先按错误比例显示，拖动后才触发重算，所以用户会看到“默认拉伸，拖一下恢复”。

解决方式：第一次收到真实 Spout 尺寸后建立比例；发送端尺寸或比例变化时，在比例锁定状态下重建目标高度。重置到主屏时按产品约定关闭比例锁定，方便用户随后自由拉伸。

### 6.5 多 GPU 和共享纹理不兼容

系统可能同时有 NVIDIA 独显和 Intel/AMD 核显。强行让接收器使用与 VTS 不同的 GPU，会导致共享纹理打开失败或跨 GPU 复制，严重时表现为瞬间卡死。

解决方式：枚举并显示 GPU，但默认跟随 Spout 发送端；切换到另一张卡时提示用户确认，并重启 VTS，使发送端和接收端回到同一适配器。

### 6.6 无上限帧率导致系统调度压力

当游戏无上限运行时，游戏、桌面合成器、浏览器视频和叠加层会同时争夺 GPU/调度时间。即使单帧绘制很快，窗口提交也可能长时间得不到执行。

解决方式：提供固定刷新率和跟随显示器刷新率，推荐先使用 60 FPS；把性能日志中的 `wake_late`、`ulw_max` 和 GPU 占用一起观察，而不是只看平均 FPS。

### 6.7 小窗口工具栏布局

固定宽度工具栏在小分辨率下会挤压 GPU 选项和按钮，出现大片空白、文字裁切或关闭按钮重复。后续改成根据窗口宽度选择单行/双行布局，调试信息单独换行，并将设置入口统一为“个性化”。

早期的 `.vendor/XboxGameBarSamples` 仅用于 Game Bar 对照，当前 CMake、启动脚本和原生渲染器均不引用它，现已删除。

## 7. 当前已知边界

- VTS 必须开启 Spout，且发送端可用；本程序不会凭空生成模型画面。
- VTS 和本程序最好运行在同一块 GPU；跨 GPU 的共享纹理不是可靠方案。
- GPU Engine 计数器受 Windows 驱动支持影响，读取不到时状态栏会显示 `--`，不会影响渲染。
- 程序仍受 Windows 桌面合成和游戏调度影响；无上限帧率并不代表任何透明叠加层都能无限流畅。
- 本项目不是游戏注入器，不修改游戏渲染管线，也不控制 Photoshop 或其他外部程序。

## 8. 启动、停止和构建

先在 VTube Studio 中开启 Spout，然后：

```powershell
.\start_overlay.cmd
```

停止：

```powershell
.\stop_overlay.cmd
```

重新编译：

```powershell
.\native\build_native.ps1 -Configuration Release
```

生成文件：

```text
VTSFloat_Meow.exe
```

常用配置和日志：

```text
%LOCALAPPDATA%\vts_overlay_layered.ini
%LOCALAPPDATA%\vts_overlay_layered.log
```

## 9. 推荐的排查顺序

1. 确认 VTS 的 Spout 已开启，并能看到发送端名称。
2. 让 VTS 和叠加层使用同一块 GPU，优先使用“GPU 自动”。
3. 先把游戏和叠加层都设为 60 FPS，确认稳定后再提高。
4. 若出现比例问题，检查“比例 锁定”；需要自由拉伸时再关闭。
5. 查看状态栏和日志：重点看 `receive_ms`、`map_scale_ms`、`ulw_ms`、`wake_late_ms`、`app_gpu_percent`。
6. 只有在确认接收和上屏稳定后，再尝试质量档或更大的窗口尺寸。
